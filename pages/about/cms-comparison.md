1C-Битрикс: Управление сайтом — система управления контентом (CMS) на основе Bitrix Framework. Разработчику, который переходит с WordPress или Joomla, нужно сопоставить привычные приемы с механизмами Bitrix:

-  где хранить контент,

-  как выбирать данные из базы,

-  как устроены шаблоны и связи между данными,

-  как подключать расширения,

-  как изменить поведение системы без правки ядра.

Каждый раздел ниже сопоставляет механизм Bitrix с WordPress и Joomla и ведет на статью с подробностями и примерами кода. Краткое соответствие — в разделе [Сравнительная таблица](#comparison-table).

Во всех трех системах файлы ядра не изменяют. Обновления Bitrix не перезаписывают папку `/local/`, поэтому доработки размещают в ней. Файлы в `/bitrix/modules/` и `/bitrix/components/bitrix/` изменять нельзя. Полный список папок, которые нельзя изменять, — в статье [Как правильно и безопасно кастомизировать коробочные продукты](../get-started/how-customize.md#where-to-place-changes).

## Работа с контентом {#content}

Bitrix хранит часть контента в файлах, а WordPress и Joomla хранят весь контент в базе данных. Группировка и связи данных описаны в разделе [Организация данных](#data-organization).

### 1C-Битрикс: Управление сайтом

В 1C-Битрикс: Управление сайтом есть два типа контента:

-  статический — данные, которые редко изменяются, например текст страниц и контакты,

-  динамический — данные, которые обновляются регулярно, например каталог товаров и новости.

Статический контент хранят в файлах. Страница — PHP-файл в структуре сайта, раздел сайта — папка с индексным файлом, например `/catalog/index.php`. Как создать страницу вручную и через интерфейс, описано в статье [Создание страницы](../get-started/create-page.md).

Динамический контент хранят в информационных блоках — инфоблоках. Информационный блок — структура для однотипных элементов, например новостей, товаров или отзывов. Основная единица динамического контента — элемент информационного блока.

У инфоблока есть фиксированный набор полей. Список свойств разработчик настраивает для каждого инфоблока отдельно. Термины модуля описаны в статье [Информационные блоки: введение и базовые концепции](../modules/iblocks/overview.md).

На сайте данные инфоблока выводят компоненты. Компонент выбирает данные и передает их шаблону, а шаблон формирует HTML. Например, список элементов выводит компонент `bitrix:news.list`, страницу одного элемента — `bitrix:news.detail`. Выбор компонента под задачу описан в статье [Вывод данных инфоблока компонентами](../modules/iblocks/components.md).

### WordPress

В WordPress основные единицы контента — запись (post) и страница. Записи используют для блога, новостей и событий, страницы — для статического контента, например страниц «О компании» и «Контакты». Запись и страница содержат текст и медиафайлы.

### Joomla

В Joomla основная единица контента — статья. Отдельную страницу сайта выводят пунктом меню, который ведет на одну статью.

## Работа с базой данных {#database}

Каждая система дает свой API для выборки данных и отдельный способ выполнить прямой SQL-запрос.

### 1C-Битрикс: Управление сайтом

Для работы с данными в Bitrix Framework есть ORM в пространстве имен `Bitrix\Main\ORM`. ORM-класс описывает таблицу и ее поля, а выборку строят методом `getList()` или построителем запросов `query()`. Принципы ORM описаны в статье [Концепция ORM](../orm/orm-concepts.md), выборка — в статье [Выборка данных](../orm/querying-data.md).

Для элементов инфоблока система создает ORM-класс, если у инфоблока задан символьный код API `API_CODE`. Классы находятся в пространстве имен `Bitrix\Iblock\Elements`. Например, для кода API `Link` система создает класс `ElementLinkTable`. Без кода API ORM-класса элементов нет. Подробнее — в разделе [Представление инфоблоков в ORM](../modules/iblocks/overview.md#iblock-orm).

Часть задач инфоблоков остается за классическим API:

-  ORM-запрос не проверяет права пользователя. Для списка с учетом прав используют `CIBlockElement::GetList()` с `'CHECK_PERMISSIONS' => 'Y'` в фильтре.

-  ORM-методы записи не обновляют поиск и не вызывают события классического API. Элементы добавляют, изменяют и удаляют методами `CIBlockElement::Add()`, `Update()`, `Delete()`.

Какой API выбрать для каждой задачи, описано в статье [Как выбрать API инфоблоков](../modules/iblocks/api.md).

Прямой SQL-запрос выполняют через объект соединения, который возвращает метод `\Bitrix\Main\Application::getConnection()`. Это аналог `$wpdb` в WordPress. Способы описаны в статье [Выполнение запросов](../database/query-execution.md).

Для данных, которые описывает документированный API, прямые запросы не используют. Такие запросы обходят встроенные механизмы безопасности и валидации. Подробнее — в разделе [Что не рекомендуется делать](../get-started/how-customize.md#not-recommended).

### WordPress

WordPress применяет класс `WP_Query` для выборки записей любого типа, включая страницы, а для прямых SQL-запросов — глобальный объект `$wpdb`.

### Joomla

Joomla работает с базой через объект драйвера `Joomla\Database\DatabaseDriver`. Запросы собирают построителем `Joomla\Database\DatabaseQuery`, который возвращает метод `createQuery()`. Прямой SQL-запрос выполняют через тот же драйвер.

## Шаблоны и отображение данных {#templates}

Bitrix, WordPress и Joomla отделяют общий макет сайта от вывода отдельных блоков страницы.

### 1C-Битрикс: Управление сайтом

1C-Битрикс: Управление сайтом использует шаблоны двух уровней — шаблон сайта и шаблон компонента.

**Шаблон сайта** задает общий макет страниц, например шапку, подвал и расположение меню. Это аналог темы WordPress и шаблона Joomla. Структура шаблона и условия его применения описаны в статье [Шаблоны сайтов](../cms-basics/site-templates.md).

**Шаблон компонента** формирует HTML одного блока страницы из данных компонента. Логика компонента находится в файле `class.php` или `component.php`, а вывод — в шаблоне. Поэтому внешний вид блока меняют без изменения логики.

У компонента может быть несколько шаблонов. Имя нужного шаблона передают вторым параметром метода `$APPLICATION->IncludeComponent()`. Если передать пустую строку `''`, система подключает шаблон `.default`. Параметры вызова описаны в разделе [Как подключить компонент](../framework/components.md#include-component).

Чтобы изменить системный шаблон компонента, его папку целиком копируют в шаблон сайта, например `/local/templates/шаблон_сайта/components/bitrix/news.list/.default/`, и правят копию. Система ищет шаблон по имени сначала в `/local/templates/`, поэтому копия с тем же именем заменяет системный шаблон без правки ядра. Это аналог переопределения макетов в Joomla. Копия под другим именем становится новым шаблоном, и ее имя передают вторым параметром `IncludeComponent()`.

Копия в `/local/templates/шаблон_сайта/` действует только для этого шаблона сайта, а копия в `/local/templates/.default/components/` — для всех шаблонов сайта. Если копии есть в обоих местах, система берет копию из шаблона сайта.

Если компонент вызван внутри комплексного компонента, например `news.list` внутри `bitrix:news`, копию кладут в шаблон комплексного компонента по пути `пространство_имен/имя_компонента/имя_шаблона/`. Например, `/local/templates/.default/components/bitrix/news/.default/bitrix/news.list/.default/`.

Система проверяет копию в шаблоне комплексного компонента первой, только если комплексный компонент передает ссылку на себя — переменную `$component` — четвертым параметром `IncludeComponent()`. Без этого параметра система ищет шаблон в обычном порядке — в текущем шаблоне сайта, в общем шаблоне сайта `.default` и в папке `templates` компонента — и копию в шаблоне комплексного компонента не использует. Порядок поиска описан в разделе [Поиск шаблона системой](../framework/components.md#template-search).

### WordPress

Классическая тема WordPress состоит из PHP-шаблонов, CSS и JavaScript. В выделенные области темы, например в боковую колонку, добавляют виджеты. Виджет содержит и логику, и вывод.

Для каждого типа контента классическая тема содержит свой PHP-файл шаблона, например `single.php` для записи и `page.php` для страницы. Чтобы изменения сохранились при обновлениях, файлы темы не редактируют, а создают дочернюю тему.

### Joomla

В Joomla шаблоны задают структуру сайта и содержат позиции, в которых размещают модули.

Компоненты в Joomla работают в рамках шаблона и отвечают за вывод основного контента страницы. Вывод компонента или модуля переопределяют копией его макета в папке `html` шаблона сайта.

## Организация данных {#data-organization}

Системы по-разному группируют данные и связывают их между собой.

### 1C-Битрикс: Управление сайтом

Информационные блоки независимы друг от друга. Каждый инфоблок можно использовать как источник данных для разных страниц сайта. Элементы инфоблока группируют в разделы с вложенными подразделами, если тип инфоблока разрешает разделы.

Связи между инфоблоками задают свойствами:

-  *Привязка к элементам* — связывает элемент с элементом любого инфоблока, например товар с товаром или статью с товаром,

-  *Привязка к разделам* — связывает элемент с разделом другого инфоблока для дополнительной категоризации.

Значение такого свойства — `ID` связанного элемента или раздела. Подробнее — в разделе [Связи между данными](../modules/iblocks/overview.md#data-links).

Для других видов данных есть два варианта:

-  Highload-блок — отдельная таблица для плоского набора записей без разделов, например справочника или сопоставления с внешней системой. Подробнее — в статье [Highload-блоки: введение и базовые концепции](../modules/highloadblocks/overview.md).

-  Собственный ORM-класс — когда схему данных полностью определяет код. Связи 1:1, 1:N и N:M между такими классами описаны в статье [Отношения между сущностями](../orm/entity-relations.md).

### WordPress

WordPress группирует записи по категориям и меткам — встроенным таксономиям. У страниц категорий и меток нет. Дополнительные данные записи хранят в произвольных полях, а собственные классификаторы создают как пользовательские таксономии. Связи между записями настраивают через произвольные поля или плагины.

### Joomla

Joomla группирует статьи по категориям, которые образуют дерево, и по тегам встроенного компонента `com_tags`. Дополнительные данные хранят в настраиваемых полях встроенного компонента `com_fields`. Структуры другого вида и связи между элементами добавляют сторонние компоненты.

## Поддержка расширений {#extensions}

Во всех трех системах новые возможности добавляют расширениями, но состав и устройство расширений различаются.

### 1C-Битрикс: Управление сайтом

Функциональность 1C-Битрикс: Управление сайтом разделена на модули, например *Интернет-магазин* `sale` и *Торговый каталог* `catalog`. Модули устанавливают и удаляют на странице *Настройки > Настройки продукта > Модули*. Модуль — ближайший аналог плагина WordPress и расширения Joomla. Готовые модули партнеров устанавливают из [Маркетплейса](https://marketplace.1c-bitrix.ru/).

Собственный код подключают двумя видами расширений:

-  Модуль — папка `/local/modules/идентификатор_модуля/` с установщиком `install/index.php` и классами в папке `lib/`. После установки модуля и вызова `\Bitrix\Main\Loader::includeModule('vendor.module')` классы из `lib/` загружаются автоматически. Пошаговый пример — в статье [Создание модуля](../get-started/create-module.md), правила автозагрузки — в статье [Автозагрузка классов](../framework/autoloading.md).

-  Компонент — папка `/local/components/пространство_имен/имя_компонента/` с логикой в `class.php` и шаблонами в `templates/`. Компонент подключают на странице методом `$APPLICATION->IncludeComponent()`, подробнее — в разделе [Как подключить компонент](../framework/components.md#include-component). Пошаговый пример — в статье [Создание компонента](../get-started/create-component.md).

В модуле путь к файлу класса в папке `lib/` повторяет имя класса после корневого пространства имен модуля. Например, для модуля `vendor.module` класс `Vendor\Module\Service\UserService` находится в файле `lib/Service/UserService.php`. Если модуль не установлен, метод `includeModule()` возвращает `false`, и классы модуля не загружаются.

### WordPress

WordPress поддерживает плагины, которые добавляют новые функции, например SEO, формы и кеширование. Собственные типы записей и таксономии регистрирует код плагина или темы.

Минимальный плагин — один PHP-файл в папке `wp-content/plugins/` с заголовочным комментарием, в котором указано имя плагина. Стили, скрипты и другие файлы добавляют при необходимости. Готовые плагины устанавливают из [каталога плагинов WordPress](https://wordpress.org/plugins/).

### Joomla

Основные типы расширений Joomla:

-  компоненты — формируют основной контент страницы,

-  модули — выводят функциональные элементы, например меню и слайдеры,

-  плагины — обрабатывают события,

-  шаблоны — задают внешний вид сайта,

-  языковые пакеты — переводят интерфейс.

Расширение устанавливают по XML-манифесту. Готовые расширения публикуют в [каталоге расширений Joomla](https://extensions.joomla.org/).

## Изменение поведения ядра {#core-behavior}

Без правки ядра поведение системы в Bitrix, WordPress и Joomla меняют разными механизмами.

### 1C-Битрикс: Управление сайтом

В Bitrix поведение ядра меняют тремя механизмами — событиями, сервисами в Service Locator и приоритетом папки `/local/`.

**События.** Модули вызывают события, а обработчики — функции или методы классов — реагируют на них. Например, событие `OnPageStart` модуля `main` вызывается в начале обработки запроса. Обработчик регистрируют одним из двух способов через объект, который возвращает метод `\Bitrix\Main\EventManager::getInstance()`:

-  Для модуля — метод `registerEventHandler()`. Его вызывают один раз при установке модуля. Регистрация хранится в базе данных. При удалении модуля регистрацию снимают методом `unRegisterEventHandler()`.

-  Для кода проекта — метод `addEventHandler()` в файле `/local/php_interface/init.php`. Такая регистрация не хранится в базе данных и действует только в текущем запросе. Ядро подключает `init.php` при каждом запуске пролога, до события `OnPageStart`. Поэтому обработчики из `init.php` работают на всех страницах, которые подключают пролог, в том числе обработчик `OnPageStart`.

Для событий классического API с аргументами по ссылке вместо `addEventHandler()` используют метод `addEventHandlerCompatible()`, а вместо `registerEventHandler()` — метод `registerEventHandlerCompatible()`.

Способ повлиять на дальнейшую логику зависит от поколения события:

-  Обработчик события D7 возвращает объект `\Bitrix\Main\EventResult`, например с типом `EventResult::ERROR`. Операция прерывается, если код, который отправил событие, проверяет результаты обработчиков и обрабатывает ошибку. Пример — в разделе [Результаты событий](../framework/events.md#event-results).

-  Обработчик классического события модуля `iblock`, например `OnBeforeIBlockElementAdd`, отменяет операцию возвратом `false`, а текст ошибки передает методом `$APPLICATION->ThrowException()`. Пример — в разделе [Отменить операцию](../modules/iblocks/events.md#cancel). У других классических событий результат обработчика зависит от конкретного события.

События — аналог `add_action()` и `add_filter()` в WordPress и плагинов Joomla. Подробнее — в статье [События](../framework/events.md).

**Сервисы в Service Locator.** Класс `\Bitrix\Main\DI\ServiceLocator` реализует интерфейс PSR-11 и создает объекты сервисов по конфигурации. Сервис регистрируют в секции `services` глобального файла настроек `/local/.settings.php` или `/bitrix/.settings.php` либо в файле `.settings.php` модуля. Сервисы модуля становятся доступны после вызова `Loader::includeModule()`.

В секции `services` массив `value` сопоставляет ключ сервиса с описанием. Ключом служит строка, имя класса или интерфейса. Описание задает способ создать объект:

-  `className` — класс реализации,

-  `constructorParams` — аргументы конструктора для класса из `className`,

-  `constructor` — замыкание, которое создает и возвращает объект.

Вызов `ServiceLocator::getInstance()->get()` возвращает объект, созданный по этому описанию. Так реализацию интерфейса задают в конфигурации, а не в коде, который ее использует.

Если класс не зарегистрирован, контейнер создает его объект по полному имени класса в режиме Autowire. Для этого зависимости конструктора должны разрешаться автоматически. Для незарегистрированного строкового ключа, который не является именем класса, метод `get()` выбрасывает исключение `\Bitrix\Main\DI\Exception\ServiceNotFoundException`.

Описание с тем же ключом в секции `services` глобального файла настроек заменяет сервис модуля. Система регистрирует сервисы глобального файла раньше и пропускает сервис модуля с уже зарегистрированным ключом. Подробнее — в статье [Service Locator](../framework/service-locator.md).

Система читает один глобальный файл настроек — `/local/.settings.php`, а если его нет, `/bitrix/.settings.php`. Настройки двух файлов не объединяются. Поэтому при создании `/local/.settings.php` в него переносят все секции из `/bitrix/.settings.php`, а не только `services`.

**Приоритет папки `/local/`.** Ядро ищет в `/local/` раньше, чем в `/bitrix/`, только определенные файлы и папки:

-  компоненты в папке `components/`,

-  шаблоны сайта и шаблоны компонентов в папке `templates/`,

-  модули в папке `modules/`,

-  файлы папки `php_interface/`, например `init.php`,

-  файлы настроек `.settings.php` и `.settings_extra.php`,

-  JS-расширения в папке `js/`.

Найденная в `/local/` версия заменяет оригинал целиком. Например, после создания `/local/php_interface/init.php` ядро перестает подключать `/bitrix/php_interface/init.php`, поэтому код из прежнего файла нужно перенести. Для остальных файлов из `/bitrix/` копия в `/local/` не действует. Подробнее — в разделе [Папка /local](../get-started/directory-structure.md#local).

Чтобы изменить вывод системного компонента, копируют его шаблон в `/local/templates/`, как описано в разделе [Шаблоны и отображение данных](#templates). Если нужна другая логика, создают собственный компонент в `/local/components/`, класс которого наследует `CBitrixComponent`. Пример класса — в разделе [Файл class.php](../framework/components.md#class-php).

### WordPress

WordPress использует событийную модель на основе хуков — действий (actions) и фильтров (filters). Функции `add_action()` и `add_filter()` подключают пользовательский код к хукам, поэтому поведение системы меняют без правки ядра.

### Joomla

Основной механизм — плагины, которые обрабатывают события. Вывод компонентов и модулей меняют переопределением макетов, как описано в разделе [Шаблоны и отображение данных](#templates).
