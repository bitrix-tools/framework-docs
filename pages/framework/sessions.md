Сессия хранит данные пользователя между его запросами к сайту, например результат авторизации, выбранные настройки и промежуточные данные форм. В Bitrix Framework с сессией работают через три механизма:

- объект сессии `Application::getSession()` — чтение и запись данных вместо прямого обращения к `$_SESSION`,
- сессионный кеш `Application::getLocalSession()` — временные данные пользователя, которые не блокируют сессию,
- секция `session` в файле `/bitrix/.settings.php` — выбор хранилища и режима работы сессии.

## Работа с сессиями

Для чтения и записи данных сессии используйте объект, который возвращает метод `getSession()` экземпляра приложения `\Bitrix\Main\Application`. Объект реализует интерфейсы `\Bitrix\Main\Session\SessionInterface` и `\ArrayAccess`, поэтому к данным можно обращаться и методами, и как к элементам массива. Не обращайтесь к `$_SESSION` напрямую. В [разделенном режиме](#separated-session-mode) до первого обращения к сессии `$_SESSION` содержит объект-обертку, а не массив, поэтому функции для массивов, например `is_array()`, работают с ним не так, как ожидается.

Ядро стартует сессию при подключении, до вывода страницы. В разделенном режиме основная сессия стартует позже, при первом обращении к данным. Если к моменту старта заголовки ответа уже отправлены, результат зависит от способа обращения:

- обращение через объект сессии, а также через `$_SESSION` до конца хита — метод `start()` выбрасывает `\RuntimeException` с текстом `Could not start session because headers have already been sent`. Для `$_SESSION` это верно, только пока основная сессия еще не стартовала. Если она уже стартовала или закрыта методом `save()`, запись в `$_SESSION` не вызывает ошибку, но и не сохраняется,
- обращение через `$_SESSION` в конце хита, после закрытия служебной сессии, — ядро пишет в лог ошибку `Skipped cold session start` и подставляет в `$_SESSION` пустой массив.

Метод `isAccessible()` объекта сессии возвращает `false`, если заголовки уже отправлены, а в настройках PHP включен параметр `session.use_cookies`. Проверяйте его перед обращением к сессии в коде, который может выполняться после вывода страницы.

**Пример.** Код записывает значение `bar` по ключу `foo`, если ключа еще нет, и выводит его:

```php
$session = \Bitrix\Main\Application::getInstance()->getSession();
if (!$session->has('foo'))
{
    $session->set('foo', 'bar');
}
echo $session['foo']; // bar
```

Основные методы объекта сессии:

| Метод | Что делает и возвращает |
|---|---|
| has($name) | Проверяет, есть ли ключ в сессии. Возвращает `bool` |
| get($name) | Возвращает значение по ключу по ссылке. Если ключа нет, создает его со значением `null` и возвращает `null`. Такой ключ сохраняется в конце хита, поэтому проверяйте наличие ключа через `has()` до вызова `get()` |
| set($name, $value) | Записывает значение по ключу. Ничего не возвращает |
| remove($name) | Удаляет ключ. Ничего не возвращает |
| clear() | Удаляет все данные сессии. Ничего не возвращает |
| getId() | Возвращает идентификатор сессии, строку |
| isStarted() | Проверяет, запущена ли сессия. Возвращает `bool` |
| save() | Сохраняет данные, закрывает сессию и снимает блокировку. В режиме `default` сессия остается закрытой до конца хита. В разделенном режиме следующее обращение к данным снова открывает сессию |
| regenerateId() | Создает новый идентификатор основной сессии. Возвращает `false`, если сессия не запущена. Не переносит сессионный кеш, поэтому для смены идентификатора используйте способ из примера ниже |
| destroy() | Удаляет сессию в хранилище, если сессия запущена. Данные в `$_SESSION` текущего хита остаются. Ничего не возвращает |

Чтобы сменить идентификатор сессии, вызовите метод `regenerateId()` менеджера сессий `getCompositeSessionManager()`. Тот же вызов ядро выполняет после входа пользователя, если включен ключ `regenerateIdAfterLogin`. Результат зависит от режима сессии:

- в режиме `default` менеджер меняет идентификатор сессии и переносит [сессионный кеш](#sessionnyj-kesh) под новый идентификатор,
- в [разделенном режиме](#separated-session-mode) менеджер меняет идентификатор только основной сессии в хранилище `general`. Идентификатор служебной сессии в cookie остается прежним. Обработчик смены идентификатора очищает группы сессионного кеша, поэтому в конце хита данные групп сохраняются пустыми.

Метод менеджера ничего не возвращает. После смены идентификатора он отправляет событие `onRegenerateSessionId` модуля `main` с параметром `newSessionId` — идентификатором служебной сессии после смены. В режиме `default` это новый идентификатор сессии, в разделенном режиме значение не меняется.

Чтобы полностью сбросить сессию, например при выходе пользователя, используйте методы `destroy()` или `clear()` менеджера `getCompositeSessionManager()`. В разделенном режиме они обрабатывают и основную сессию, и служебные данные в cookie. Методы объекта сессии `getSession()` действуют только на основную сессию.

**Пример.** Код полностью удаляет сессию пользователя в обоих режимах:

```php
\Bitrix\Main\Application::getInstance()->getCompositeSessionManager()->destroy();
```

**Пример.** Код меняет идентификатор сессии, например после смены прав пользователя:

```php
\Bitrix\Main\Application::getInstance()->getCompositeSessionManager()->regenerateId();
```

## Сессионный кеш

Сессионный кеш хранит временные данные текущего пользователя, например список просмотренных товаров или настройки фильтра. В отличие от данных сессии, он не блокирует параллельные запросы пользователя, если кеш хранится в памяти, например в Memcache, Redis или APC. Сохранять в самой сессии большие объемы данных не рекомендуется, потому что каждый хит читает и записывает сессию целиком и ждет ее блокировки.

Метод `getLocalSession($name)` экземпляра приложения возвращает объект [\\Bitrix\\Main\\Data\\LocalStorage\\SessionLocalStorage](https://docs.1c-bitrix.ru/api/classes/Bitrix-Main-Data-LocalStorage-SessionLocalStorage.html). Параметр `$name` — имя группы данных, например `someCategory`. Объект работает как массив и поддерживает методы `get()`, `set()` и `clear()`.

**Пример.** Код записывает в группу `someCategory` два значения, если их еще нет, и выводит список товаров:

```php
$localStorage = \Bitrix\Main\Application::getInstance()->getLocalSession('someCategory');
if (!isset($localStorage['productIds']))
{
    $localStorage->set('productIds', [1, 2, 100]);
    $localStorage->set('price', 42);
}

var_dump($localStorage->get('productIds'));
```

Как работает сессионный кеш:

- Данные группы хранятся под ключом, который состоит из идентификатора сессии и имени группы. Пользователи не видят данные друг друга.
- При первом обращении к группе ядро читает ее данные из хранилища. Если данных нет, объект пустой.
- Ядро сохраняет все группы в конце хита, в обработчике события `OnAfterEpilog`. Если хит завершился раньше этого события, изменения не сохранятся.
- При хранении в кеше данные живут 86400 секунд, то есть сутки. Срок задают в секции `session_local_storage` файла `/bitrix/.settings.php`, например `'session_local_storage' => ['value' => ['ttl' => 3600]]`. При хранении в `$_SESSION` срок не действует, данные живут столько же, сколько сессия.
- При смене идентификатора сессии в режиме `default` данные групп переносятся под новый идентификатор, в разделенном режиме — очищаются. Подробности описаны в разделе [Работа с сессиями](#rabota-s-sessiyami).

Хранилище сессионного кеша зависит от типа кеша в секции `cache` файла `.settings.php`. При кеше в памяти, например в Memcache, Redis или APC, данные хранятся в кеше. При файловом кеше и при выключенном кеше данные хранятся в обычной сессии `$_SESSION`, и тогда они блокируются вместе с ней. Настройка кеша описана в статье [Кеширование](../performance/caching.md).

## Виды сессии

Константы `BX_SECURITY_SESSION_READONLY` и `BX_SECURITY_SESSION_VIRTUAL` меняют поведение сессии для одного хита. Обе константы задают [до подключения ядра](./request-lifecycle.md), например в начале файла AJAX-обработчика перед подключением `prolog_before.php`.

### Неблокирующие сессии

Обычная сессия блокируется на время хита, поэтому параллельные AJAX-запросы одного пользователя выполняются по очереди. Если хит только читает сессию, установите константу `BX_SECURITY_SESSION_READONLY`.

**Пример.** AJAX-обработчик включает чтение сессии без блокировки, подключает ядро и читает значение из сессии:

```php
<?php
define('BX_SECURITY_SESSION_READONLY', true);
require $_SERVER['DOCUMENT_ROOT'] . '/bitrix/modules/main/include/prolog_before.php';

$session = \Bitrix\Main\Application::getInstance()->getSession();
echo $session->get('foo');
```

С этой константой обработчик хранилища читает сессию без ожидания блокировки и не записывает ее в конце хита. Изменения, которые хит внес в сессию, теряются.

Константа работает при хранении сессии в Redis, Memcache и базе данных. При хранении в файлах константа не действует, PHP блокирует файл сессии и записывает его как обычно.

Без константы второй хит ждет, пока первый освободит сессию. Время ожидания зависит от хранилища:

- в базе данных хит ждет блокировку до 60 секунд. Если сессия так и не освободилась, ядро завершает хит с кодом ответа 500 и ошибкой `Unable to get session lock within 60 seconds`,
- в Redis и Memcache ключ блокировки живет 55 секунд. Ожидающий хит получает сессию не позже чем через 55 секунд, даже если первый хит еще работает, и ошибки не возникает.

Учитывайте также таймауты веб-сервера. Например, nginx по умолчанию ждет ответ PHP 60 секунд и может завершить долгий хит своей ошибкой раньше ядра.

Чтобы найти страницу, которая держит блокировку в Redis или Memcache, включите ключ `exclusiveLock` обработчика.

### Виртуальные сессии

Если хиту сессия не нужна, установите константу `BX_SECURITY_SESSION_VIRTUAL`. Сессия существует только в памяти хита и не читается из хранилища и не сохраняется в него. Константа отменяет настройки секции `session` для этого хита. Ядро использует виртуальную сессию, например, при обработке REST-запросов, в которых нет параметров `sessid`, `livechat_auth_id` и `call_auth_id`.

**Пример.** Константа включает виртуальную сессию:

```php
define('BX_SECURITY_SESSION_VIRTUAL', true);
```

## Конфигурация хранения данных

Хранилище сессий задают в секции `session` файла `/bitrix/.settings.php`. Общие правила работы с этим файлом описаны в статье [Конфигурация ядра](./settings.md).

Для хранения данных сессии используют четыре типа хранилища. Тип указывают в ключе `type` обработчика `general`. Служебный тип `array` ядро использует для виртуальной сессии, тип `null` работает так же. Данные эти типы не хранят.

| Тип | Хранилище | Неблокирующие сессии |
|---|---|---|
| `file` | Файлы в папке из настройки `session.save_path` PHP | Не поддерживаются |
| `redis` | Сервер Redis, нужно расширение PHP `redis` | Поддерживаются |
| `memcache` | Сервер Memcache, нужно расширение PHP `memcache` | Поддерживаются |
| `database` | Таблица базы данных сайта, MySQL или PostgreSQL | Поддерживаются |

Если секции `session` в файле нет или в ней задан только ключ `'mode' => 'default'`, ядро выбирает хранилище так:

- если в настройке `session.save_handler` PHP указано `files`, ядро хранит сессии в файлах,
- если указано другое значение, например `redis`, ядро использует обработчик из настроек PHP и не меняет его.

При неизвестном значении `type` ядро выбрасывает исключение `\Bitrix\Main\NotSupportedException` с текстом `Unknown session handler`, и сайт не открывается.

Файлы подходят для одного веб-сервера. Если сайт работает на нескольких серверах, используйте Redis, Memcache или базу данных. Файлы сессий на разных серверах не видны друг другу.

### Хранение в файлах

**Пример.** Секция `session` хранит сессии в файлах:

```php
// bitrix/.settings.php
return [
    // ...
    'session' => [
        'value' => [
            'mode' => 'default',
            'handlers' => [
                'general' => [
                    'type' => 'file',
                ],
            ],
        ],
    ],
];
```

Ключ `savePath` обработчика `general` задает папку для файлов сессий, например `'savePath' => '/var/lib/php/sessions'`. Значение принимает и формат настройки PHP `N;MODE;/path`. Если в значении больше двух символов `;`, ядро выбрасывает `ArgumentException` с текстом `Invalid format for savePath`. Если ключ не указан, ядро берет папку из настройки `session.save_path` PHP. Если папки нет, ядро пытается ее создать.

### Использование Redis

Для хранения сессий в Redis на сервере должно быть установлено расширение PHP `redis`. Без него ядро выбрасывает исключение `NotSupportedException` с текстом `redis extension is not loaded.`.

**Пример.** Секция `session` хранит сессии на одном сервере Redis:

```php
// bitrix/.settings.php
return [
    // ...
    'session' => [
        'value' => [
            'mode' => 'default',
            'handlers' => [
                'general' => [
                    'type' => 'redis',
                    'host' => '127.0.0.1',
                    'port' => 6379,
                ],
            ],
        ],
    ],
];
```

Ключи обработчика `redis`:

| Ключ | Описание |
|---|---|
| host<br>`string` | Адрес сервера. По умолчанию `127.0.0.1`. Для подключения через сокет укажите путь с префиксом `unix://`, тогда порт не используется |
| port<br>`int` | Порт сервера. По умолчанию `6379` |
| password<br>`string` | Пароль сервера. Ядро передает пароль только при подключении к одному серверу. Если единственный сервер задан в `servers`, пароль указывают в ключе `password` элемента списка. При подключении к кластеру ядро пароль не передает |
| servers<br>`array` | Список серверов кластера. Каждый элемент — массив с ключами `host` и `port`. Если ключ задан, ключи `host` и `port` верхнего уровня не используются |
| keyPrefix<br>`string` | Префикс ключей сессий в Redis. По умолчанию `BX`. Задайте разные префиксы, если один сервер Redis хранит сессии нескольких сайтов |
| exclusiveLock<br>`bool` | Записывать в ключ блокировки адрес страницы, которая заблокировала сессию. Адрес хранится в значении ключа `<keyPrefix><id сессии>.lock`, его можно прочитать в хранилище. По умолчанию `false` |
| serializer<br>`int` | Сериализатор расширения `redis`, например `\Redis::SERIALIZER_IGBINARY`. По умолчанию igbinary, если расширение `redis` собрано с поддержкой igbinary, иначе сериализатор PHP |
| persistent<br>`bool` | Использовать постоянное соединение. По умолчанию для одного сервера `false`, для кластера `true` |
| timeout<br>`float` | Время ожидания подключения в секундах. По умолчанию `0` — действует настройка PHP `default_socket_timeout` |
| readTimeout<br>`float` | Время ожидания ответа сервера в секундах. По умолчанию `0` — действует настройка PHP `default_socket_timeout` |
| failover<br>`int` | Режим чтения с реплик кластера, константа `\RedisCluster::FAILOVER_*`. Действует, только если в `servers` больше одного сервера. По умолчанию `\RedisCluster::FAILOVER_NONE` |

Срок хранения сессии в Redis равен значению настройки `session.gc_maxlifetime` PHP. Ядро задает его при каждой записи сессии.

Если расширение `redis` собрано с поддержкой LZ4, ядро сжимает данные сессий этим алгоритмом. Через секцию `session` сжатие не отключается. Учитывайте это, если ключи сессий читают другие программы.

Чтобы подключиться к Redis Cluster, перечислите узлы кластера в ключе `servers`. Если в списке больше одного сервера, ядро создает подключение `\RedisCluster`, и кластер сам распределяет ключи по узлам. Если в списке один сервер, ядро создает обычное подключение `\Redis` к этому серверу.

**Пример.** Секция `session` хранит сессии в Redis Cluster из трех узлов:

```php
// bitrix/.settings.php
return [
    // ...
    'session' => [
        'value' => [
            'mode' => 'default',
            'handlers' => [
                'general' => [
                    'type' => 'redis',
                    'servers' => [
                        [
                            'host' => '127.0.0.1',
                            'port' => 6379,
                        ],
                        [
                            'host' => '127.0.0.2',
                            'port' => 6379,
                        ],
                        [
                            'host' => '127.0.0.3',
                            'port' => 6379,
                        ],
                    ],
                    'serializer' => \Redis::SERIALIZER_IGBINARY,
                    'persistent' => false,
                    'failover' => \RedisCluster::FAILOVER_DISTRIBUTE,
                    'timeout' => 2,
                    'readTimeout' => 2,
                ],
            ],
        ],
    ],
];
```

Значение `\RedisCluster::FAILOVER_DISTRIBUTE` распределяет чтение между основными узлами и репликами. Константа `\Redis::SERIALIZER_IGBINARY` есть, только если расширение `redis` собрано с поддержкой igbinary. Иначе уберите ключ `serializer` из настроек, и ядро выберет сериализатор само.

### Использование Memcache

Для хранения сессий в Memcache на сервере должно быть установлено расширение PHP `memcache`. Без него ядро выбрасывает исключение `NotSupportedException` с текстом `memcache extension is not loaded.`.

**Пример.** Секция `session` хранит сессии на одном сервере Memcache:

```php
// bitrix/.settings.php
return [
    // ...
    'session' => [
        'value' => [
            'mode' => 'default',
            'handlers' => [
                'general' => [
                    'type' => 'memcache',
                    'host' => '127.0.0.1',
                    'port' => 11211,
                ],
            ],
        ],
    ],
];
```

Ключи обработчика `memcache`:

| Ключ | Описание |
|---|---|
| host<br>`string` | Адрес первого сервера. По умолчанию `127.0.0.1` |
| port<br>`int` | Порт первого сервера. По умолчанию `11211` |
| servers<br>`array` | Дополнительные серверы. Каждый элемент — массив с ключами `host`, `port` и `weight` |
| weight<br>`int` | Ключ элемента `servers`. Вес сервера при распределении ключей, целое число больше нуля. По умолчанию `1` |
| connectionTimeout<br>`int` | Время ожидания подключения в секундах. По умолчанию `1` |
| keyPrefix<br>`string` | Префикс ключей сессий в Memcache. По умолчанию `BX` |
| exclusiveLock<br>`bool` | Записывать в ключ блокировки адрес страницы, которая заблокировала сессию. Адрес хранится в значении ключа `<keyPrefix><id сессии>.lock`, его можно прочитать в хранилище. По умолчанию `false` |

Ядро всегда ставит сервер из ключей `host` и `port` первым в списке серверов, даже если задан ключ `servers`. Поэтому не повторяйте этот сервер в `servers`, иначе он попадет в список дважды. Срок хранения сессии в Memcache равен значению настройки `session.gc_maxlifetime` PHP.

**Пример.** Секция `session` распределяет сессии между двумя серверами Memcache. Первый сервер задан ключами `host` и `port`, второй — в `servers`:

```php
// bitrix/.settings.php
return [
    // ...
    'session' => [
        'value' => [
            'mode' => 'default',
            'handlers' => [
                'general' => [
                    'type' => 'memcache',
                    'host' => '127.0.0.1',
                    'port' => 11211,
                    'servers' => [
                        [
                            'host' => '127.0.0.2',
                            'port' => 11211,
                            'weight' => 1,
                        ],
                    ],
                ],
            ],
        ],
    ],
];
```

### Хранение в базе данных

Сессии хранятся в таблице базы данных сайта, с ней работает ORM-класс `\Bitrix\Main\Session\Handlers\Table\UserSessionTable`. Блокировку сессии ядро получает средствами базы данных. Она поддерживается для MySQL и PostgreSQL. Устаревшие записи ядро удаляет при сборке мусора сессий PHP, срок задает настройка `session.gc_maxlifetime`.

**Пример.** Секция `session` хранит сессии в базе данных:

```php
// bitrix/.settings.php
return [
    // ...
    'session' => [
        'value' => [
            'mode' => 'default',
            'handlers' => [
                'general' => [
                    'type' => 'database',
                ],
            ],
        ],
    ],
];
```

## Дополнительные настройки

Кроме обработчиков, секция `session` содержит ключи режима и поведения сессии.

**Пример.** Секция `session` хранит сессии в Redis, меняет идентификатор сессии после входа пользователя и продолжает хит без сессии, если Redis недоступен:

```php
// bitrix/.settings.php
return [
    // ...
    'session' => [
        'value' => [
            'mode' => 'default',
            'regenerateIdAfterLogin' => true,
            'ignoreSessionStartErrors' => true,
            'handlers' => [
                'general' => [
                    'type' => 'redis',
                    'host' => '127.0.0.1',
                    'port' => 6379,
                ],
            ],
        ],
    ],
];
```

Ключи секции `session`:

| Ключ | Описание |
|---|---|
| mode<br>`string` | Режим сессии. `default` — обычная сессия, `separated` — [разделенный режим](#separated-session-mode). По умолчанию `default` |
| handlers<br>`array` | Обработчики хранилища. Ключ `general` — хранилище данных сессии, ключ `kernel` — хранилище служебных данных в разделенном режиме. Если `general` не задан, ядро хранит сессии в файлах, кроме случая из раздела [Конфигурация хранения данных](#konfiguraciya-hraneniya-dannyh), когда используется обработчик из настроек PHP |
| lifetime<br>`int` | Время жизни зашифрованной cookie со служебными данными в секундах. Действует только в разделенном режиме. По умолчанию `0` — cookie живет до закрытия браузера |
| regenerateIdAfterLogin<br>`bool` | Создавать новый идентификатор сессии после успешного входа пользователя. Защищает от фиксации идентификатора сессии. По умолчанию `false` |
| ignoreSessionStartErrors<br>`bool` | Подавлять ошибку старта сессии — исключение `Could not start session by PHP` и ошибки PHP `\Error` при вызове `session_start()`. По умолчанию `false`. Флаг не гарантирует, что хит продолжит работу без хранилища. Проверка на стенде показала, что при недоступном Redis расширение `redis` выбрасывает `RedisException`, которое флаг не перехватывает, а при недоступном Memcache хит завершается ошибкой `TypeError` еще при подключении ядра, когда ядро обращается к данным сессии |

Время жизни данных сессии в режиме `default` задает настройка `session.gc_maxlifetime` PHP.

## Разделенный режим сессии {#separated-session-mode}

В разделенном режиме сессия делится на две части. Служебные данные ядра, например данные авторизации, хранятся в зашифрованной cookie и не блокируют параллельные запросы. Остальные данные хранятся в хранилище обработчика `general` и блокируются только при первом обращении к ним. Подробно режим описан в статье [Сессия в разделенном режиме](../performance/hot-and-cold-session.md).

Чтобы включить разделенный режим, измените секцию `session` в файле `/bitrix/.settings.php`.

1. Укажите `'mode' => 'separated'`.

2. Задайте `lifetime` — время жизни cookie со служебными данными в секундах, например `14400`, то есть четыре часа.

3. Добавьте в `handlers` ключ `'kernel' => 'encrypted_cookies'`.

**Пример.** Секция `session` включает разделенный режим, служебные данные хранятся в cookie четыре часа, остальные данные — в файлах:

```php
// bitrix/.settings.php
return [
    // ...
    'session' => [
        'value' => [
            'mode' => 'separated',
            'lifetime' => 14400,
            'handlers' => [
                'kernel' => 'encrypted_cookies',
                'general' => [
                    'type' => 'file',
                ],
            ],
        ],
    ],
];
```

Ядро проверяет настройки разделенного режима при старте и выбрасывает исключение `\Bitrix\Main\NotSupportedException` в двух случаях:

- в `handlers` нет ключа `kernel`, текст ошибки `There is no handler for kernel session`,
- ключ `kernel` содержит значение, отличное от `encrypted_cookies`, текст ошибки `Invalid settings. Kernel session works only with "encrypted_cookies"`.

Чтобы временно выключить разделенный режим без правки `.settings.php`, задайте константу `BX_FORCE_DISABLE_SEPARATED_SESSION_MODE` со значением `true` до подключения ядра. Ядро будет работать в режиме `default` с тем же обработчиком `general`.
