Направление объединяет элементы одного типа CRM. Если тип использует стадии, каждому направлению соответствует свой набор. Стадия показывает положение элемента в процессе. Например, сделка находится в работе или завершена. Направления и стадии получают через фабрику типа, а изменения элемента сохраняют через операцию этой фабрики.

В интерфейсе направления также называют воронками. В PHP API направление представлено категорией `Bitrix\Crm\Category\Entity\Category`. Общую модель `Factory → Item → Operation` объясняет статья [Схема работы CRM и основные объекты API](./architecture.md).

Для перехода элемента используйте настроенные направления и стадии. Если смарт-процессу нужно еще одно направление, сначала выполните сценарий [«Добавить направление»](./smart-processes.md#add-category).

## Различать тип, направление и стадию

Для выбора стадии нужны тип элемента и его направление. Название стадии подходит для показа пользователю, но при записи нужно передать строковый код.

#|
|| **Значение** | **Что обозначает** | **Где получить и использовать** ||
|| `entityTypeId` | Тип элемента CRM | Передать в `Container::getFactory()` ||
|| `CATEGORY_ID` | Категорию элемента. Для типа с направлениями — выбранное направление | Получить через `Category::getId()`, задать элементу через `setCategoryId()` ||
|| `STAGE_ID` | Строковый код стадии элемента | Получить через `EO_Status::getStatusId()`, задать через `Item::setStageId()` ||
|| `EO_Status::getId()` | Числовой ID записи о стадии | Не передавать вместо строкового `STAGE_ID` ||
|| `ENTITY_ID` набора стадий | Группу статусов, к которой относятся стадии направления | Получить через `Factory::getStagesEntityId($categoryId)`. Это не `entityTypeId` ||
|#

Метод `Factory::getStagesEntityId()` возвращает, например, `DEAL_STAGE` для основного направления сделок и `DEAL_STAGE_<categoryId>` для дополнительного. У лида группа называется `STATUS`. Формировать эти значения вручную не требуется. Метод `getStages()` сам выбирает нужную группу.

У сделок основное направление имеет ID `0`. У смарт-процесса направление по умолчанию — отдельная запись со своим ID. Не используйте `0` как универсальный ID основного направления и не считайте нулевую категорию сделки ошибкой.

### Проверить возможности типа

Поддержка категорий и поддержка стадий — разные возможности. Контакты и компании поддерживают категории, но не стадии. У лида есть стадии без направлений. У смарт-процесса доступность направлений и стадий зависит от настроек типа.

Проверяйте методы выбранной фабрики.

-  `isCategoriesSupported()` — поддерживает ли тип категории на уровне API.

-  `isCategoriesEnabled()` — включены ли направления в интерфейсе типа.

-  `isStagesSupported()` — поддерживает ли тип стадии.

-  `isStagesEnabled()` — включены ли стадии с учетом настроек типа.

Для чтения категорий достаточно поддержки API. Для перехода стадии проверьте `isStagesEnabled()`. Если метод вернул `false`, не задавайте `STAGE_ID`. У смарт-процесса категория остается частью модели и при выключенных направлениях в интерфейсе. Настройки типа описаны в статье [Смарт-процессы](./smart-processes.md#type-settings).

## Подготовить фабрику и пользователя {#prepare-factory-and-user}

Перед выполнением подключите пролог и модуль `crm`. Код запускайте в серверном обработчике приложения. Для HTTP-запроса проверяйте авторизацию и защиту от CSRF до изменения CRM.

Переменная `$userId` должна содержать положительный ID пользователя, от имени которого работает обработчик или фоновое задание. Получайте его из доверенного контекста приложения. Не принимайте произвольный ID пользователя из запроса клиента.

Передавайте ID пользователя, типа, элемента и категорий как `int`, а коды стадий — как `string`. ID пользователя и элемента должны быть больше нуля. Для категории сделки допустим `0`. Типы важны при строгом сравнении запрошенных и сохраненных значений.

**Пример.** Подготовьте фабрику сделок и сервис проверки прав для пользователя `$userId`. Для смарт-процесса замените `CCrmOwnerType::Deal` на его `entityTypeId`.

```php
if (!\Bitrix\Main\Loader::includeModule('crm'))
{
    throw new \RuntimeException('Не удалось подключить модуль CRM');
}

if ($userId <= 0)
{
    throw new \RuntimeException('Не задан пользователь операции');
}

$entityTypeId = \CCrmOwnerType::Deal;
$container = \Bitrix\Crm\Service\Container::getInstance();
$factory = $container->getFactory($entityTypeId);
if ($factory === null)
{
    throw new \RuntimeException('Фабрика выбранного типа недоступна');
}

$permissions = $container->getUserPermissions($userId);
```

Остальные примеры используют подготовленные `$factory`, `$permissions`, `$entityTypeId` и `$userId`. ID элементов и направлений, а также коды стадий передавайте из проверенных данных приложения.

Для записи создайте объект `Bitrix\Crm\Service\Context`, задайте пользователя через `setUserId($userId)` и передайте контекст в `getAddOperation()` или `getUpdateOperation()`. Тогда чтение и проверка прав операции используют одного пользователя. Объект `$permissions` сам по себе не задает пользователя операции.

## Получить направления и стадии

Сначала определите направление, затем запросите его стадии. Фабрика читает конфигурацию CRM без отбора по правам пользователя. Для пользовательского списка отдельно примените фильтры прав.

### Найти доступное направление

Для чтения используйте методы фабрики.

-  `getCategories()` возвращает массив объектов `Category` выбранного типа.

-  `getCategory($categoryId)` находит категорию по ID или возвращает `null`.

-  `getDefaultCategory()` возвращает категорию по умолчанию либо `null`, если она не найдена.

Метод `isCategoryAvailable($categoryId)` проверяет существование и доступность категории для использования, включая ограничения типа. Он не проверяет права конкретного пользователя. Для списка, в котором пользователь выбирает направление для чтения, используйте `category()->filterAvailableForReadingCategories()`.

**Пример.** Получите названия и ID направлений, доступных пользователю для чтения. Если тип не поддерживает категории, массив `$categoryData` останется пустым.

```php
$categoryData = [];
if ($factory->isCategoriesSupported())
{
    $categories = $permissions->category()->filterAvailableForReadingCategories(
        $factory->getCategories()
    );

    foreach ($categories as $category)
    {
        if (!$factory->isCategoryAvailable($category->getId()))
        {
            continue;
        }

        $categoryData[] = [
            'id' => $category->getId(),
            'name' => $category->getName(),
            'isDefault' => $category->getIsDefault(),
        ];
    }
}
```

Каждая запись массива `$categoryData` содержит три ключа.

-  `id` — ID категории.

-  `name` — название.

-  `isDefault` — признак категории по умолчанию.

Перед выводом названий в HTML экранируйте их.

Для выбора направления при создании элемента используйте `category()->filterAvailableForAddingCategories()`. Право читать элементы направления не означает право добавлять их. При переносе существующего элемента дополнительно требуется право изменить сам элемент.

Метод `createDefaultCategoryIfNotExist()` может создать категорию или назначить существующую категорией по умолчанию. Для простого чтения используйте `getDefaultCategory()`. В смарт-процессе запрос стадий без явного ID категории также может вызвать создание направления по умолчанию. Чтобы чтение не меняло конфигурацию, сначала найдите существующую категорию и передайте ее ID.

### Прочитать стадии выбранного направления {#get-category-stages}

Метод `getStages($categoryId)` возвращает коллекцию `Bitrix\Crm\EO_Status_Collection`. Стадии упорядочены по полю `SORT`. Для типа без направлений вызовите `getStages()` без ID категории. Перед чтением убедитесь, что стадии включены.

Метод `stage()->canReadInStage($entityTypeId, $categoryId, $stageId)` возвращает `true`, если пользователь может читать элементы в стадии. Передайте тип CRM, ID категории и строковый код стадии. Для типа без категорий передавайте `$categoryId = null`. Это же значение допустимо в `getStages()` и `getStageFromCategory()` для такого типа.

**Пример.** Получите стадии основного направления сделок с ID `0`, доступные пользователю для чтения. Для смарт-процесса передайте ID существующего направления вместо `0`.

```php
$categoryId = 0;
if (!$factory->isStagesEnabled())
{
    throw new \RuntimeException('Стадии для выбранного типа выключены');
}

if ($factory->isCategoriesSupported())
{
    $category = $factory->getCategory($categoryId);
    if (
        $category === null
        || !$factory->isCategoryAvailable($categoryId)
        || !$permissions->category()->canReadItems($category)
    )
    {
        throw new \RuntimeException('Направление не найдено или недоступно');
    }
}
else
{
    $categoryId = null;
}

$stages = $factory->getStages($categoryId);
$stageData = [];
foreach ($stages as $stage)
{
    $stageId = $stage->getStatusId();
    if (!$permissions->stage()->canReadInStage($entityTypeId, $categoryId, $stageId))
    {
        continue;
    }

    $stageData[] = [
        'stageId' => $stageId,
        'name' => $stage->getName(),
        'semantics' => $factory->getStageSemantics($stageId),
    ];
}
```

Каждая запись массива `$stageData` содержит три ключа.

-  `stageId` — код для записи в элемент.

-  `name` — название для показа.

-  `semantics` — смысл стадии, описанный в разделе [«Определить рабочую и финальную стадию»](#working-and-final-stages).

Пустой массив означает, что код не нашел стадий, доступных пользователю для чтения. Он не подтверждает отсутствие стадий в конфигурации.

Метод `getStage($stageId)` ищет стадию среди направлений типа. Для проверки принадлежности выбранному направлению используйте `getStageFromCategory($categoryId, $stageId)`. Метод возвращает объект стадии или `null`. Проверка по названию ненадежна. Названия можно изменить, а стадии разных направлений могут называться одинаково.

Список стадий для чтения не является списком разрешенных переходов конкретного элемента. Право перехода зависит от исходной и целевой стадий, элемента и пользователя. Его проверяет сценарий [«Изменить стадию элемента»](#change-stage).

### Определить рабочую и финальную стадию {#working-and-final-stages}

Семантика объединяет стадии по результату процесса. Класс `Bitrix\Crm\PhaseSemantics` определяет три значения.

#|
|| **Константа** | **Значение** | **Смысл** ||
|| `PhaseSemantics::PROCESS` | `P` | Элемент находится в работе ||
|| `PhaseSemantics::SUCCESS` | `S` | Процесс завершен успешно ||
|| `PhaseSemantics::FAILURE` | `F` | Процесс завершен неуспешно ||
|#

Метод `getStageSemantics($stageId)` возвращает семантику стадии или `null`, если стадия не найдена. Для найденной стадии без определенной семантики метод возвращает `PROCESS`. Поэтому для определения результата используйте семантику, а не название, позицию стадии в списке или фрагмент ее кода.

Метод `getSuccessfulStage($categoryId)` возвращает успешную стадию выбранного направления либо `null`. Если нужно выбрать одну из причин неуспеха, просмотрите `getStages($categoryId)` и отберите стадии с семантикой `FAILURE`. Конкретную причину выбирает приложение или пользователь.

**Пример.** Получите код успешной стадии направления `$categoryId`. Код только выбирает стадию, но не изменяет элемент и не проверяет право перехода.

```php
$successfulStage = $factory->getSuccessfulStage($categoryId);
if ($successfulStage === null)
{
    throw new \RuntimeException('Успешная стадия направления не найдена');
}

$targetStageId = $successfulStage->getStatusId();
```

Для возврата из финальной стадии в работу выберите существующую стадию с семантикой `PROCESS` и выполните обычную операцию перехода. Не меняйте вручную признак закрытия или вычисляемую семантику элемента вместо `STAGE_ID`.

### Найти элементы в направлении и стадии

После выбора направления можно прочитать его элементы через `getItemsFilteredByPermissions()`. Передайте ID пользователя, чтобы выборка учитывала его права. Параметр `filter` ограничивает направление и стадию, `order` задает порядок, `limit` — размер порции.

**Пример.** Получите не более 20 элементов направления `$categoryId` в стадии `$targetStageId`. Фабрика должна поддерживать категории и включенные стадии, а пара значений — пройти проверку через `getStageFromCategory()`.

```php
$items = $factory->getItemsFilteredByPermissions([
    'filter' => [
        '=CATEGORY_ID' => $categoryId,
        '=STAGE_ID' => $targetStageId,
    ],
    'order' => ['ID' => 'ASC'],
    'limit' => 20,
], $userId);
```

Для типа без категорий уберите `CATEGORY_ID` из фильтра. В фабричном API используйте общее имя `STAGE_ID`. Для лида фабрика сопоставляет его с `STATUS_ID`. Чтение больших наборов и продолжение после сбоя описаны в статье [Работа с элементами CRM](./items.md#process-items-in-batches).

## Создать элемент в выбранном направлении {#create-item-in-category}

У нового элемента сначала задайте направление через `setCategoryId()`, затем выберите начальную стадию. Метод `setStartStageIdPermittedForUser($item, $userId)` устанавливает первую стадию направления, в которой пользователю разрешено добавление, и возвращает ее код. Если подходящей стадии нет, метод возвращает `null`.

Метод предназначен для нового элемента. Для существующего элемента он не подбирает другую стадию, а возвращает текущую. Если стадии выключены, пропустите вызов и создайте элемент без `STAGE_ID`.

**Пример.** Создайте сделку в направлении `$categoryId`, выбранном из доступных для добавления. Сначала выполните [подготовку фабрики и пользователя](#prepare-factory-and-user). Для другого типа дополните пример его обязательными полями.

```php
if (!$factory->isCategoriesSupported())
{
    throw new \RuntimeException('Тип не поддерживает направления');
}

$category = $factory->getCategory($categoryId);
if (
    $category === null
    || !$factory->isCategoryAvailable($categoryId)
    || !$permissions->category()->canAddItems($category)
)
{
    throw new \RuntimeException('Добавление в направление недоступно');
}

$item = $factory->createItem();
$item->setCategoryId($categoryId);
$item->set(\Bitrix\Crm\Item::FIELD_NAME_TITLE, 'Новая сделка');

if ($factory->isStagesEnabled())
{
    $startStageId = $factory->setStartStageIdPermittedForUser($item, $userId);
    if ($startStageId === null)
    {
        throw new \RuntimeException('Нет доступной начальной стадии');
    }
}

$context = (new \Bitrix\Crm\Service\Context())->setUserId($userId);
$result = $factory->getAddOperation($item, $context)->launch();
if (!$result->isSuccess())
{
    throw new \RuntimeException(implode('; ', $result->getErrorMessages()));
}

$itemId = $item->getId();
```

После успеха переменная `$itemId` содержит ID нового элемента. Операция повторно проверяет права и обязательные поля.

Если правило приложения требует конкретной начальной стадии, выберите ее через `getStageFromCategory()` и проверьте право добавления методом `stage()->canAddInStage($entityTypeId, $categoryId, $stageId)`. Передайте тип CRM, ID выбранного направления и строковый код стадии. Метод возвращает `bool`. При `false` остановите добавление, при `true` задайте код через `setStageId($stageId)` и запустите операцию. В таком сценарии не вызывайте `setStartStageIdPermittedForUser()`, который выбирает стадию самостоятельно.

Общий порядок добавления и защита от повторного создания после ошибки приведены в статье [Работа с элементами CRM](./items.md#create-item).

## Изменить стадию элемента {#change-stage}

Переход внутри направления выполняйте через `setStageId()` и `getUpdateOperation()`. Перед записью проверьте три условия.

1. Стадия относится к текущему направлению.

2. Пользователь может изменить элемент.

3. Пользователю разрешен переход из текущей стадии в выбранную.

Метод `item()->canChangeStage($itemIdentifier, $fromStageId, $toStageId)` проверяет право перехода. Объект `Bitrix\Crm\ItemIdentifier` задает тип, ID и категорию элемента. Он создается через `ItemIdentifier::createByItem($item)`. Аргументы `$fromStageId` и `$toStageId` — строковые коды исходной и целевой стадий.

### Проверить переход и сохранить стадию {#check-transition-and-save-stage}

Для одного элемента сначала прочитайте запись с учетом прав пользователя. Пустая выборка означает, что элемент отсутствует или недоступен для чтения. Проверка права чтения не заменяет проверку изменения.

**Пример.** Переведите элемент `$itemId` в стадию `$targetStageId` текущего направления. Передайте положительный ID элемента и строковый код, выбранный из списка стадий. Сначала выполните [подготовку фабрики и пользователя](#prepare-factory-and-user).

```php
if (!$factory->isStagesEnabled())
{
    throw new \RuntimeException('Стадии для выбранного типа выключены');
}

$items = $factory->getItemsFilteredByPermissions([
    'filter' => ['=ID' => $itemId],
    'limit' => 1,
], $userId);
$item = $items[0] ?? null;
if ($item === null)
{
    throw new \RuntimeException('Элемент не найден или недоступен');
}

$categoryId = $factory->isCategoriesSupported() ? $item->getCategoryId() : null;
if ($factory->getStageFromCategory($categoryId, $targetStageId) === null)
{
    throw new \RuntimeException('Стадия не принадлежит направлению элемента');
}

if (!$permissions->item()->canUpdateItem($item))
{
    throw new \RuntimeException('Нет права изменить элемент');
}

$sourceStageId = $item->getStageId();
if ($sourceStageId !== $targetStageId)
{
    $identifier = \Bitrix\Crm\ItemIdentifier::createByItem($item);
    if (!$permissions->item()->canChangeStage($identifier, $sourceStageId, $targetStageId))
    {
        throw new \RuntimeException('Переход в выбранную стадию запрещен');
    }

    $item->setStageId($targetStageId);
    $context = (new \Bitrix\Crm\Service\Context())->setUserId($userId);
    $result = $factory->getUpdateOperation($item, $context)->launch();
    if (!$result->isSuccess())
    {
        throw new \RuntimeException(implode('; ', $result->getErrorMessages()));
    }
}
```

Код не запускает операцию, если элемент уже находится в нужной стадии. Метод `setStageId()` меняет объект в памяти, а `launch()` выполняет проверки и сохранение. Предварительные проверки помогают обработать ошибку до записи, но не заменяют проверки самой операции. Права и данные могли измениться.

Для построения списка допустимых переходов переберите стадии текущего направления и примените `canChangeStage()` к каждой целевой стадии. Сначала проверьте `canUpdateItem()` для элемента. Не считайте следующую по `SORT` стадию автоматически разрешенной.

### Учесть обязательные поля и завершение

При смене стадии могут потребоваться поля, обязательные для нового этапа. После задания стадии получите их список методом `getRequiredFields()` операции по статье [Поля и данные клиента](./fields-and-client-data.md#required-operation-fields). Заполните поля до `launch()` или верните пользователю ошибки из `getErrorMessages()`. Не отключайте проверки обязательных полей и прав, чтобы принудительно завершить переход.

{% note warning "" %}

Неверный код стадии не всегда приводит к ошибке операции. Если направление существующего элемента не меняется, обработчик стадии может восстановить прежнее значение. Поэтому проверяйте код через `getStageFromCategory()` и после операции подтверждайте фактическую стадию повторным чтением.

{% endnote %}

Операция обновляет историю, запускает автоматизацию и бизнес-процессы в зависимости от типа и настроек CRM. Переход в финальную стадию также может автоматически завершить дела поддерживаемых провайдеров. Прямое сохранение поля через ORM не заменяет этот сценарий. Порядок действий и ограничения результата описаны в статье [Схема работы CRM и основные объекты API](./architecture.md#operation-save-steps).

Для лида изменение `STAGE_ID` означает изменение статуса. Оно не создает контакт, компанию или сделку. Для преобразования лида используйте отдельный сценарий [«Конвертировать лид»](./items.md#convert-lead).

## Перенести элемент в другое направление

Для переноса выберите новое направление и стадию именно этого направления. Задайте `CATEGORY_ID` и `STAGE_ID` одному объекту `Item`, затем запустите одну операцию изменения. Перенос не меняет тип и ID элемента.

Пользователю нужны право изменить исходный элемент и право добавлять элементы в целевое направление. Проверка `canChangeStage()` относится к переходам внутри направления. При смене категории CRM использует отдельную проверку доступа к целевому направлению.

### Проверить доступ и сохранить направление {#check-access-and-save-category}

Проверяйте целевую категорию до изменения объекта `Item`. После выбора стадии передайте оба значения одной операции.

**Пример.** Перенесите сделку или элемент смарт-процесса `$itemId` в `$targetCategoryId` и `$targetStageId`. Сначала выполните [подготовку фабрики и пользователя](#prepare-factory-and-user). Направление и стадия должны существовать. Для переноса в основное направление сделок допустим `$targetCategoryId = 0`.

```php
if (!$factory->isCategoriesSupported() || !$factory->isStagesEnabled())
{
    throw new \RuntimeException('Для примера нужны направления и включенные стадии');
}

$items = $factory->getItemsFilteredByPermissions([
    'filter' => ['=ID' => $itemId],
    'limit' => 1,
], $userId);
$item = $items[0] ?? null;
if ($item === null || !$permissions->item()->canUpdateItem($item))
{
    throw new \RuntimeException('Элемент недоступен для изменения');
}

if ($item->getCategoryId() === $targetCategoryId)
{
    throw new \RuntimeException('Для текущего направления используйте переход стадии');
}

$targetCategory = $factory->getCategory($targetCategoryId);
if (
    $targetCategory === null
    || !$factory->isCategoryAvailable($targetCategoryId)
    || !$permissions->category()->canAddItems($targetCategory)
)
{
    throw new \RuntimeException('Целевое направление недоступно для добавления');
}

if ($factory->getStageFromCategory($targetCategoryId, $targetStageId) === null)
{
    throw new \RuntimeException('Стадия не принадлежит целевому направлению');
}

$item->setCategoryId($targetCategoryId);
$item->setStageId($targetStageId);

$context = (new \Bitrix\Crm\Service\Context())->setUserId($userId);
$result = $factory->getUpdateOperation($item, $context)->launch();
if (!$result->isSuccess())
{
    throw new \RuntimeException(implode('; ', $result->getErrorMessages()));
}
```

Если у смарт-процесса стадии выключены, меняйте только категорию. Проверки существования, доступности направления и права добавления в него остаются нужны. Для лида используйте переход стадии внутри типа. Его фабрика не поддерживает направления.

### Учесть подбор стадии и обязательные поля {#stage-selection-and-required-fields}

При смене направления без подходящего `STAGE_ID` CRM пытается подобрать первую стадию нового направления с той же семантикой. Семантику определяет код, который находится в объекте `Item` перед обработкой. Если оставить прежний код успешной стадии, CRM ищет успешную стадию нового направления. Если задать неизвестный код, CRM использует семантику `PROCESS`, даже если до изменения элемент был завершен успешно.

Автоматический подбор не сопоставляет стадии по названиям. Если подходящей стадии нет, обработчик возвращает ошибку. Передайте существующий код целевой стадии в `setStageId()`, чтобы приложение определяло результат переноса.

Обязательность полей при смене направления проверяется иначе, чем при обычном переходе стадии. В операции изменения смена категории включает проверку обязательности только изменяемых полей. Если приложение должно обеспечить заполненность всех полей нового этапа, проверьте это отдельным бизнес-правилом до переноса. Успешная операция переноса сама по себе не подтверждает такую полноту данных.

## Проверить результат и повторить действие

Метод `Result::isSuccess()` показывает, что операция не добавила ошибок в результат. Он не гарантирует нужную стадию после всех обработчиков и не подтверждает успешное завершение роботов. После перехода или переноса перечитайте элемент и сравните фактические значения с ожидаемыми.

**Пример.** Проверьте сохраненную пару направления и стадии. Для обычного перехода `$expectedCategoryId` содержит исходное направление, для переноса — целевое. Переменная `$expectedStageId` содержит запрошенный код стадии. Код выполняется в доверенном серверном обработчике после операции.

```php
$savedItem = $factory->getItem($itemId);
if ($savedItem === null)
{
    throw new \RuntimeException('Элемент не найден при проверке результата');
}

$categoryMatches = !$factory->isCategoriesSupported()
    || $savedItem->getCategoryId() === $expectedCategoryId;
$stageMatches = !$factory->isStagesEnabled()
    || $savedItem->getStageId() === $expectedStageId;

$matchesExpectedState = $categoryMatches && $stageMatches;
```

Переменная `$matchesExpectedState` равна `true`, если сохраненные значения соответствуют ожидаемым. Метод `getItem()` не проверяет права чтения. В этом примере он нужен для внутренней сверки. Перед передачей данных пользователю отдельно проверьте доступ. После переноса пользователь может потерять право читать элемент в новом направлении.

При ошибке операции также перечитайте запись. Ошибка могла возникнуть после сохранения. Если нужная пара уже записана, разберите сбой связанного действия, прежде чем повторять переход.

Для разбора повторных команд сохраняйте в журнале приложения следующие данные.

-  Тип и ID элемента.

-  Исходные и целевые направление и стадию.

-  ID пользователя операции.

-  Результат операции и фактическое состояние после нее.

Чтение и последующее изменение не блокируют параллельный переход другим обработчиком. Для фоновой интеграции согласуйте правило конфликтов и не повторяйте старую команду поверх нового состояния без проверки. Сценарий повторного изменения приведен в статье [Работа с элементами CRM](./items.md#retry-update).

Направление и стадию выбирайте из конфигурации конкретного типа, проверяйте права пользователя и сохраняйте изменения через операцию фабрики. Повторное чтение подтверждает, что элемент оказался в том направлении и на той стадии, которые требовались приложению.
