ORM D7 дает доступ к внутренней структуре инфоблоков. Ниже собраны пространства имен модуля, генерируемые ORM-классы `Element{ApiCode}Table` и `Section{ID}Table`, карты классов, поля ORM-классов и типы свойств. Используйте материал как справочник полей и типов при написании запросов и выборе типа свойства. Пошаговые задачи описаны в статьях [Работа с элементами инфоблока](./elements.md), [Выборка элементов инфоблока](./element-queries.md) и [Создание и настройка инфоблоков](./setup.md).

Во всех примерах модуль подключен методом `\Bitrix\Main\Loader::includeModule('iblock')`.

## Основные пространства имен модуля

Архитектура D7 организует классы по пространствам имен. Для работы с инфоблоками через ORM используйте соответствующие пространства имен.

```php
use Bitrix\Iblock\TypeTable; // Типы инфоблоков
use Bitrix\Iblock\IblockTable; // Инфоблоки
use Bitrix\Iblock\SectionTable; // Разделы
use Bitrix\Iblock\ElementTable; // Элементы
use Bitrix\Iblock\PropertyTable; // Свойства
```

## Генерируемые классы: структура и иерархия

Для инфоблока с заполненным `API_CODE` система автоматически создает три связанных ORM-класса в пространстве имен `\Bitrix\Iblock\Elements\`.

1. `Element{ApiCode}Table` — статический класс-таблица. Через него читают элементы методами `getList()`, `getByPrimary()` и `query()`. Методы `add()`, `update()` и `delete()` у класса есть, но элементы добавляйте, изменяйте и удаляйте методами `CIBlockElement`, подробнее — в разделе [Как выбрать API инфоблоков](./api.md#api-boundaries).

2. `EO_Element{ApiCode}` — класс-объект. Представляет одну запись. Через него читают поля, например `$element->getId()` и `$element->getName()`.

3. `EO_Element{ApiCode}_Collection` — класс-коллекция. Представляет набор объектов-записей, которые перебирают в цикле.

Для разделов создается аналогичная тройка классов, но в именах используется `ID` инфоблока: `Section{ID}Table`, `EO_Section{ID}`, `EO_Section{ID}_Collection`. Класс разделов создает метод `Bitrix\Iblock\Model\Section::compileEntityByIblock()`, способ описан в разделе [Получить ORM-класс разделов](./sections.md#get-orm-class).

**Пример.** Прочитайте активные элементы инфоблока с символьным кодом API `Clothes` через три класса.

```php
use Bitrix\Iblock\Elements\ElementClothesTable;

// 1. Table: получаем данные
$collection = ElementClothesTable::getList([
    'select' => ['ID', 'NAME'],
    'filter' => ['=ACTIVE' => 'Y'],
])->fetchCollection();

// 2. Collection: перебираем набор
foreach ($collection as $element)
{
    // 3. Object: читаем поля записи
    echo $element->getId() . ': ' . $element->getName();
}
```

Изменение элементов описано в разделе [Изменить элемент](./elements.md#update-element).

### Архитектура наследования

Сгенерированные классы не создаются с нуля, они наследуют базовую логику от общих классов модуля. Это обеспечивает единый механизм работы для всех инфоблоков.

1. **Повторное использование кода.** Стандартная логика CRUD-операций (Create, Read, Update and Delete) реализована в базовых классах.

2. **Специализация.** Ваш класс автоматически знает структуру именно вашего инфоблока: свойства и поля.

3. **Расширяемость.** Вы можете унаследовать сгенерированный класс и добавить свою логику.

Схема формирования класса для элементов.

```plain text
\Bitrix\Iblock\ElementTable — общая карта и таблица элементов
         │
         │ getTableName() и getMap()
         ↓
\Bitrix\Iblock\ORM\CommonElementTable — общая логика элементов инфоблока
         ↑
\Bitrix\Iblock\ORM\ElementV1Table или \Bitrix\Iblock\ORM\ElementV2Table — база по версии хранения свойств
         ↑
\Bitrix\Iblock\Elements\Element{ApiCode}Table — ваш класс для работы с элементами конкретного инфоблока
```

Система выбирает базовый класс по полю `VERSION` инфоблока:

-  `ElementV1Table` — если свойства хранятся в общей таблице,

-  `ElementV2Table` — если свойства хранятся в отдельных таблицах инфоблока.

Класс `Element{ApiCode}Table` создается при первом обращении к нему или при вызове `IblockTable::compileEntity()`. Для класса автоматически задается фильтр по `IBLOCK_ID`, поэтому запросы через него работают с элементами конкретного инфоблока.

Схема наследования для разделов.

```plain text
\Bitrix\Iblock\SectionTable — общая таблица разделов
         ↑
\Bitrix\Iblock\Section{ID}Table — ваш класс для работы с разделами конкретного инфоблока
```

**Пример.** Расширение класса для инфоблока с `API_CODE` = `Clothes`.

```php
namespace Partner\Catalog;

// Создаем свой класс на основе сгенерированного
class MyClothesTable extends \Bitrix\Iblock\Elements\ElementClothesTable
{
    public static function getActiveClothes(): \Bitrix\Iblock\Elements\EO_ElementClothes_Collection
    {
        return static::getList([
            'filter' => ['=ACTIVE' => 'Y'],
            'order' => ['SORT' => 'ASC']
        ])->fetchCollection();
    }
}
```

Расширяйте сгенерированный класс в своем пространстве имен. Не меняйте класс `Element{ApiCode}Table` напрямую: он создается системой и зависит от настроек инфоблока.

Добавляйте в наследник методы для типовых выборок, проверок и логики проекта.

Не используйте наследование для изменения структуры системной карты полей. Для наследников от `Element{ApiCode}Table` ORM берет уже скомпилированную карту родительского класса, поэтому переопределение `getMap()` в таком наследнике не добавит поля в карту элемента.

Если нужно получить вычисляемое поле только в одном запросе, добавьте его как `runtime`-поле.

```php
use Bitrix\Iblock\Elements\ElementClothesTable;
use Bitrix\Main\ORM\Fields\ExpressionField;

$items = ElementClothesTable::query()
    ->registerRuntimeField(
        new ExpressionField(
            'NAME_LENGTH',
            'LENGTH(%s)',
            ['NAME']
        )
    )
    ->setSelect(['ID', 'NAME', 'NAME_LENGTH'])
    ->fetchAll()
;
```

В результате в выборке появится поле `NAME_LENGTH`. Оно действует только в этом запросе и не меняет карту класса.

## Карты классов

Каждый ORM-класс содержит метод `getMap()`. Он возвращает описание структуры таблицы: поля, типы полей, связи с другими ORM-классами и правила валидации. Система использует карту класса для следующих задач:

-  строит SQL-запросы,

-  преобразует данные между PHP и базой данных,

-  проверяет типы данных при сохранении,

-  организует связи между таблицами.

Классы вида `Element{ApiCode}Table` получают расширенную карту: базовые поля элементов и свойства инфоблока с заполненным `CODE` как связи ORM.

### Как свойства попадают в карту {#property-map}

Метод `getMap()` базового класса элемента возвращает поля таблицы `b_iblock_element`. Свойства конкретного инфоблока добавляются в карту при компиляции класса `Element{ApiCode}Table`.

В карту попадают только свойства с заполненным полем `CODE`. Код свойства становится именем поля в ORM-запросе. Например, свойство с кодом `BRAND` доступно как поле `BRAND`.

Проверить наличие поля можно через объект ORM-класса.

```php
use Bitrix\Iblock\Elements\ElementClothesTable;

if (ElementClothesTable::getEntity()->hasField('BRAND'))
{
    // Свойство BRAND доступно в карте класса
}
```

Для каждого свойства система создает отдельный ORM-класс значения вида `IblockProperty{ID}Table`. В этом классе есть поле `VALUE`, а если у свойства включено описание — поле `DESCRIPTION`.

Тип связи зависит от множественности свойства:

-  одиночное свойство добавляется как связь `PropertyReference` — наследник `Reference`,

-  множественное свойство добавляется как связь `PropertyOneToMany` — наследник `OneToMany`.

Базовый тип свойства определяет тип поля `VALUE`:

-  строка — `StringField`,

-  число — `FloatField`,

-  файл, список, привязка к элементу или разделу — `IntegerField`.

Для некоторых типов система добавляет дополнительные связи. Например, для свойства Файл появляется связь `FILE` с таблицей файлов, для свойства Список — связь `ITEM` со значением списка, для свойства Привязка к разделу — связь `SECTION`.

Пользовательский тип свойства может расширить карту значения свойства через обработчик `GetORMFields`. Обработчик задают ключом `GetORMFields` в описании пользовательского типа. При компиляции класса элементов система вызывает его с двумя аргументами — описанием ORM-класса значения `Bitrix\Main\ORM\Entity` и объектом свойства, обработчик добавляет поля методом `addField()` описания. Этот способ подходит, когда нужно добавить поля именно к ORM-классу значения свойства.

Для добавления обычных данных к элементу используйте свойства инфоблока, а для временных вычислений в запросе — `runtime`-поля.

Как выбрать значения свойств в запросе, описано в разделе [Прочитать значения](./property-values.md#read-values), как отфильтровать элементы по свойству — в разделе [Отфильтровать по свойству](./element-queries.md#filter-by-property).

{% note warning "" %}

Не добавляйте в наследниках `Element{ApiCode}Table` свои поля с именами системных полей или свойств инфоблока. Такое расширение может нарушить сохранение свойств, связи ORM и работу с версиями хранения `VERSION = 1` и `VERSION = 2`.

{% endnote %}

### Формат ответа

Метод `getMap()` возвращает данные в одном из двух форматов, в зависимости от реализации класса.

1. Массив объектов полей — современный формат. Каждый элемент массива — объект, который наследуется от `Bitrix\Main\ORM\Fields\Field`. Например, `StringField`, `IntegerField`, `Reference` и так далее. Имя поля задается в конструкторе объекта. Ключи массива могут совпадать с именами полей, как в `ElementTable`, но ORM берет имя поля из объекта.

   Подход обеспечивает строгую типизацию, поддержку валидаторов, модификаторов, связей и расширяемость.

2. Ассоциативный массив с именами полей в качестве ключей — устаревший формат. Каждый ключ — имя поля, значение — массив с описанием `data_type`, `title`, `validation` и так далее. Не поддерживает сложные типы полей и объектную логику.

Начало ответа метода `getMap()` для `ElementTable` — ключ массива совпадает с именем поля, значение — объект поля.

```php
Array
(
    [ID] => Bitrix\Main\ORM\Fields\IntegerField Object
        (
            [name:protected] => ID
            [is_primary:protected] => 1
            [is_autocomplete:protected] => 1
            ...
        )

    [TIMESTAMP_X] => Bitrix\Main\ORM\Fields\DatetimeField Object
        (
            [name:protected] => TIMESTAMP_X
            ...
        )
    ...
)
```

## Описание полей классов таблиц

Данные модуля хранятся в отдельных таблицах. Каждой таблице соответствует класс в ORM. Для обращения к данным используйте эти классы.

`ID` — первичный ключ объекта, числовой у инфоблока, раздела, элемента и свойства и строковый у типа инфоблоков. По этому ключу система связывает данные между таблицами.

{% note info "" %}

Звездочкой \* отмечены поля, которые не могут быть пустыми в таблице. Поля со значением по умолчанию и вычисляемые поля, например `ID` и `TIMESTAMP_X`, при добавлении передавать не нужно. Минимальный набор полей для добавления элемента приведен в разделе [Подготовить поля](./elements.md#prepare-fields).

{% endnote %}

Параметры применяются ко всем инфоблокам одного типа. Создание типа в коде описано в разделе [Создать тип инфоблоков](./setup.md#create-type).

{% note warning "" %}

Для инфоблоков с `VERSION = 2` методы `PropertyTable::add()`, `PropertyTable::update()` и `PropertyTable::delete()` выполняются без ошибки, но не меняют таблицы значений. Значения свойства, добавленного через `PropertyTable::add()`, не сохраняются, а после `PropertyTable::delete()` в таблице остается колонка. Управляйте свойствами таких инфоблоков методами классического API `CIBlockProperty` или в административном интерфейсе, способ описан в разделе [Выбрать API для настройки](./setup.md#choose-api).

{% endnote %}

## Свойства

Свойства позволяют расширять базовую структуру элементов информационных блоков. Например, можно добавить цвет к товару, теги к статье, файл к документу. Система поддерживает базовые и пользовательские типы свойств. У каждого типа свойства есть свои особенности и ограничения.

### Базовые типы свойств

#### Строка `S`

Значение хранится как текст. Длина текста ограничена типом поля базы данных.

В форме редактирования можно задавать визуальные ограничения через поля `ROW_COUNT` и `COL_COUNT`. Значение по умолчанию должно быть строкой, числом или булевым значением. Массивы не поддерживаются.

#### Число `N`

Значение хранится как число. Операции сортировки и сравнения работают с числами.

Пустое значение система воспринимает как `NULL`. Строку, которую нельзя привести к числу, система не принимает и отдает ошибку при фильтрации или сохранении. Значение по умолчанию должно быть числом или строкой, которую можно привести к числу.

#### Список `L`

Значения списка хранятся в отдельной таблице `b_iblock_property_enum`. Пользователь выбирает значение из заранее заданного списка.

Каждое значение списка `VALUE` должно содержать непустой текст. Ограничения на `XML_ID` зависят от способа добавления варианта и описаны в разделе [Добавить варианты в существующий список](./setup.md#add-enum-values). Система проверяет, используют ли элементы значения списка, перед их удалением или изменением.

#### Файл `F`

Значение хранит идентификатор файла из таблицы `b_file`. Вы можете ограничивать типы загружаемых файлов через маску в поле `FILE_TYPE`.

Каждый загружаемый файл проходит проверку через систему `CFile`. Система проверяет размер файла, расширение и другие параметры.

#### Привязка к элементу `E`

Значение — `ID` элемента другого инфоблока. Если в настройках свойства задано поле `LINK_IBLOCK_ID`, то значение должно ссылаться на элемент существующего инфоблока.

Система проверяет существование элемента при сохранении. В ORM у значения такого свойства есть поле `ELEMENT` — объект связанного элемента, если у связанного инфоблока задан символьный код API.

#### Привязка к разделу `G`

Значение — `ID` раздела инфоблока. Система проверяет, что раздел существует и принадлежит указанному инфоблоку. В ORM у значения такого свойства есть связь `SECTION` с разделом.

### Пользовательские типы свойств {#user-property-types}

Система предоставляет дополнительные типы свойств. Они расширяют базовые типы и добавляют специальную логику.

#### Типы модуля Информационные блоки

Модуль `iblock` включает набор встроенных типов свойств. Они доступны везде, где установлен модуль, и расширяют базовые типы дополнительной логикой и интерфейсом.

-  `Date` и `DateTime` — для работы с датами и временем. Используют виджеты выбора даты.

-  `ElementXmlID` — привязка к элементу по внешнему идентификатору `XML_ID` для обмена данными.

-  `FileMan` — путь к файлу в структуре сайта. Использует диалог выбора файлов.

-  `HTML` — текст в формате HTML с визуальным редактором. Не поддерживает множественные значения.

-  `EList` — выпадающий список элементов из другого инфоблока. Аналогичен типу Привязка к элементу `E` , но с отдельным интерфейсом.

-  `Sequence` — автоматический счетчик. Значение увеличивается при создании каждого нового элемента.

-  `EAutocomplete` и `SectionAuto` — привязка к элементам и разделам с автодополнением.

#### Типы других модулей

Специализированные модули добавляют свои типы свойств. Эти типы становятся доступны после установки соответствующего модуля и обеспечивают интеграцию с его функциональностью.

-  `SKU` — связь с торговыми предложениями из модуля Торговый каталог.

-  `ECrm` — привязка к объектам CRM: лидам, сделкам, контактам, компаниям и так далее.

-  `Money` — денежная сумма с указанием валюты.

-  `DiskFile` — файл из модуля Диск.

-  `map_google`, `map_yandex` — координаты на карте.

-  `TopicID` — привязка к теме форума.

-  `directory` — связь с highload-блоком.

-  `UserID` — привязка к пользователям.

-  `employee` — привязка к сотрудникам.

### Ограничения при создании и обновлении свойства {#property-limits}

Система проверяет свойства при сохранении. Основные ограничения:

-  Поле `NAME` обязательное и не может быть пустым.

-  Поле `CODE` должно соответствовать правилам:

   -  не может начинаться с цифры,

   -  может содержать только латинские буквы, цифры и символ подчеркивания.

   Уникальность кода в пределах инфоблока система не проверяет — следите за ней самостоятельно. Эти правила действуют только для кода свойства. Для символьного кода элементов и разделов система не ограничивает набор символов, подробнее — в разделе [Символьные коды](./overview.md#symbolic-codes).

-  Поле `IBLOCK_ID` должно ссылаться на существующий инфоблок.

-  Для простых типов без `USER_TYPE` значение `DEFAULT_VALUE` должно быть скалярным — массив или объект вызовут ошибку.

-  Если свойство обязательное `IS_REQUIRED = 'Y'`, система проверяет, чтобы значение было заполнено при сохранении элемента.

#### Особенности привязки к элементам и разделам

Для типов свойств привязка к элементу `E` и привязка к разделу `G` действуют дополнительные правила.

-  Система ожидает целочисленный `ID` элемента или раздела.

-  Если задан `LINK_IBLOCK_ID`, значение должно ссылаться на объект из указанного инфоблока.

-  Где хранятся значения, зависит от версии хранения инфоблока, подробнее — в разделе [Версии хранения свойств](./overview.md#property-storage-versions).

-  В ORM у значения свойства типа `E` есть поле `ELEMENT`, у типа `G` — связь `SECTION`.

Эти ограничения обеспечивают целостность данных и правильную работу фильтрации и сортировки.

### Как выбрать тип свойства

Выбор типа свойства влияет на хранение данных, производительность и возможности фильтрации.

#### Число или строка

Используйте тип Число `N`:

-  для сортировки значений по величине,

-  применения диапазонных фильтров,

-  вычислений или агрегации данных.

Примеры: цены, веса, рейтинги, вычисление суммы или средних значений.

Используйте тип Строка `S`, если:

-  значение содержит буквы и специальные символы,

-  важнее поиск по подстроке, чем числовые операции,

-  значение имеет сложный формат.

Примеры: артикулы, коды, сложные значения вида `A-001-2025`.

#### Список, справочник или привязка

Обычный список `L` подходит:

-  для небольшого набора значений,

-  значений, которые редко меняются,

-  простого управления через форму свойства.

Примеры: статусы, типы, цвета из короткого списка.

Справочник на highload-блоке `directory` используйте:

-  для большого количества значений в сотнях или тысячах,

-  значений с дополнительными полями, например, изображениями, кодами, сортировкой,

-  сложных классификаторов, которые требуют отдельного управления.

Привязку к элементам `E` или разделам `G` рекомендуется использовать, когда:

-  значение представляет собой самостоятельный объект с собственной логикой,

-  нужны обратные связи и сложные выборки через ORM,

-  значение имеет свою карточку с дополнительными полями.

#### Когда применять пользовательские типы

Пользовательские типы решают конкретные задачи. Применяйте их, когда базовых типов недостаточно для требуемого поведения или интерфейса.

-  `HTML` — для текста с форматированием: описания, статьи.

-  `Date`**/**`DateTime` — для отдельных дат: дата поставки, начало акции.

-  `Sequence` — для автоматической нумерации: номера заказов, документов.

-  `ElementXmlID` — для интеграции с внешними системами по внешним ключам.

-  `ECrm`, `UserID` — для связи с объектами CRM или пользователями.

-  `map_*` — для хранения координат на карте.

#### Множественные значения и описания

Опция `MULTIPLE = 'Y'` дает возможность указывать для свойства несколько значений, например, цветов, размеров, связанных товаров.

Опция `WITH_DESCRIPTION = 'Y'` позволяет добавить текстовый комментарий к каждому значению свойства. Опция не зависит от множественности: ее можно включить и для одиночного, и для множественного свойства типов Строка `S`, Число `N` и Файл `F`.

{% note info "" %}

Некоторые пользовательские типы ограничивают множественность. Например, тип `HTML` не поддерживает множественные значения.

{% endnote %}

## Ограничения ORM-записи {#backward-compatibility}

ORM-классы инфоблоков не вызывают события классического API и выполняют при записи только часть его работы. Что делает только классический API и какой API выбрать для каждой задачи, описано в статье [Как выбрать API инфоблоков](./api.md#api-boundaries). Какие способы записи вызывают события классического API, описано в статье [События инфоблоков](./events.md#which-events).
